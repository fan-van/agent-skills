# 代码层面的逻辑解析

用户是程序员，需要通过真实代码和数据流看懂实现。默认中文。用户已认可的讲解方式是“按真实执行顺序展示关键源码 + 紧贴代码标明真实表名和字段 + 解释每步目的及后续用途”。用一组数据串起读、算、判断、写、再读取的过程。关系图用于帮助串联，不能替代这些代码和落库说明；不要默认输出长篇业务说明或整套数据库字段字典。

用户有其他语言的编程基础，需要学习 Python 等当前语言的不同规则。默认不解释变量是什么、字符串是什么、点号/引号/括号/if 等通用基础，也不逐个拆解每个符号。只有用户具体追问时才进一步展开。

## 简明解释语言差异，并串起整段逻辑

默认采用“关键代码 + 两三条必要的语言规则 + 一句整段业务含义”。复杂数据流再补具体表字段的读写关系；短表达式不要展开成整套系统讲解。

- 优先解释当前语言特有或容易跨语言误解的规则。例如 Python dict.get 缺键返回 None，而下标取值会抛 KeyError；or 返回操作数而非固定返回布尔值，x or "" 会对所有假值使用空字符串；and/or 短路求值、is None 与相等比较的区别。
- 语法规则紧贴原代码说明，不做通用运算符词典，不重复解释用户已经理解的基础。必要时只代入一组值，展示关键变化，不逐步列出所有 True/False。
- 讲完整句究竟筛选什么、为何继续或跳过，以及与下一段业务代码的关系；不能只讲局部语法，也不能让一句代码的解释散成多页。
- 用户说“没懂”时，定位尚未讲清的语言规则或数据连接并补充，不自动退回零基础逐字符教学，不机械扩写所有步骤。
- 引用字段的来源、实际表名和写入列仍要明确。保持简洁不能重新变成“保存一下”“登记一下”的黑盒。

## 先核实代码

- 阅读实际入口、调用函数、模型和相关读写代码，遵守项目的检索约定。
- 区分当前实现、本地修改和设计建议；代码阅读确认与运行验证也要分清。
- 关键代码给真实文件绝对路径及行号。不能编造表、字段、历史版本表、查询或测试结果。
- 保留真实变量名、函数名、表名和字段名，方便用户直接回到代码定位。

## 默认输出方式

### 按用户认可的读写闭环组织

按真实代码依次展开相关步骤，不机械凑步骤数量：

1. **生成并保存**：数据由哪行赋值得到，哪个 INSERT/create/save 写入哪张真实表；给出“表.字段 ← 变量”的映射。
2. **读取**：展示 ORM/SQL 的条件、真实表名和返回字段，说明查询结果装进哪个变量。
3. **处理与判断**：展示对这个变量的实际字段读取、计算和比较；解释为什么比较，成功/失败各走哪里。
4. **写入下一条记录**：展示实际写入方法及对应 db_table，说明关联键、金额、完整内容各自写哪一列。
5. **日志与后续使用**：代码若写事件或审计日志，明确日志表及关联键；再说明业务后续从哪里读回已存数据。

每个写入步骤应让用户直接对上，例如：

~~~text
Reservationdiscount.objects.create(...) → 实际表 reservationdiscount
  reservationdiscount.bill_id       ← row['id']，来自已读取的 bill.id
  reservationdiscount.amount        ← quote['amount']，本次优惠结果
  reservationdiscount.rule_snapshot ← snapshot，完整规则JSON
~~~

以上仅示范表达方式。必须先核实当前项目确实存在这些模型、表和字段。不能只写“保存成功”“登记优惠”“记录日志”，也不能只列模型类名而省略实际数据库表名。

每步配必要的短源码和解释，避免把整段原函数一次性贴完。先把用户当前追问的环节讲清，其他环节只保留连接闭环所需的内容。

使用关系图时，图本身必须能独立读懂：每个首次出现的方法，就地注释其职责、关键输入和输出；每个变量或字段，注明它是数据库表/列、内存列表/字典还是标量，以及业务含义和必要的示例值。不能只写 rules、result、winner、snapshot 等名称让用户猜，也不能只在很远的正文中解释。图和源码的顺序按问题调整，避免用一张很长的图推迟关键解释。

特别区分同名或同结构对象：promotions.quote(...) 是方法调用，quote = ... 中左边的 quote 是接收返回值的局部变量；result、promotion、quote 可能是在不同函数中命名不同的同结构返回数据。图中说明函数嵌套调用，不得把“quote 内部调用 evaluate_rules 后组装结果”误画成彼此独立的先后函数阶段。

~~~text
promotionrule 表：当前优惠规则
    │ 查询，读取完整规则内容
    ▼
内存 rules → evaluate_rules(...) → result
    │ result['snapshot'] 组装完整规则副本，尚未落库
    ▼
quote['snapshot'] → snapshot
    │ Reservationdiscount.objects.create(...)
    ▼
reservationdiscount 表
  bill_id       = 对应账单的 bill.id
  rule_snapshot = snapshot 完整 JSON
    │ 后续按酒店编号、订单号查询
    ▼
读取 rule_snapshot → evaluate_rules(...) → 新计算结果
~~~

这是表达结构的示例。每次使用必须按实际源码重建关系，不得把示例当成所有项目的实现。程序实际从订单查询优惠记录时，不能把一条可行的反向 SQL 当成实际执行路径。

### 再按执行顺序分步引用代码

每步采用下面的形式，步数按实际逻辑决定，不限定为三步：

每一步都要补业务因果：执行前还有哪个具体问题没解决，为什么需要这次查询/判断/赋值，这段代码如何解决它，结果被下一步怎样消费。仅把函数名翻译成“查规则”“计算优惠”“组装结果”仍不够。结合同一组输入值走一遍判断和计算，说明为何保留某字段、为何要复制整份规则、为何不能只存计算金额；这些理由须与实际实现一致。让用户知道整个函数如何完成调用方的需求，而不只是知道其中存在若干计算。

1. 一句话说明这一步做什么，以及由谁在什么时候触发。
2. 链接到具体文件和行号。
3. 展示最小但足够理解的真实代码片段；使用正确的语言代码块，例如 Python 使用 python。
4. 在代码赋值处用简短注释解释字段含义、值的来源和用途。
5. 紧跟代码说明结果交给谁，以及此时是在内存中还是已经写入数据库。

不要先输出大量抽象说明，再在结尾补几行代码。不要用字段表或业务叙事替代实际调用、赋值、查询和写入过程。

## 每段代码必须接得上前后

围绕同一笔示例数据，按需要说明：

- 输入从哪里来：请求参数、数据库查询、上一步返回值还是配置。
- 用什么查什么：具体 ORM/SQL/API，过滤字段和参数分别是什么。
- 返回什么：对象、列表、ID、完整 JSON 或计算结果；给理解所需的结构。
- 如何处理：具体条件判断、字段比较、计算和分支，以及判断目的。
- 传给谁：指出上一步返回键如何赋给下一步变量，不能跳过中间转换。
- 如何保存：哪个函数写哪个表、哪个字段，关联键由哪条记录产生。
- 遇到 ORM create/save/update，紧贴代码写出实际数据库表名和写入列；检查模型 Meta.db_table，不能只给用户一个类名。读回也要指明从哪个真实表按什么条件读取。副本、来源标记、金额、事件日志各自存哪里必须分开说明，不得以“登记优惠”“保存副本”“记录日志”概括而不展示写入方法。使用“表.列 ← 右侧变量”的映射把输入追踪到持久化，标明哪些只是内存变量、哪些是此前已写入的记录。
- 后续怎么用：谁再次查询这条记录，取出哪些字段，怎样重新进入计算或业务结果。
- 失败怎么办：针对当前问题说明查不到、校验失败、异常和事务回滚，不展开无关风险清单。

例如 result['snapshot'] → quote['snapshot'] → snapshot → rule_snapshot，必须说明 result 是哪个函数的返回值、quote 如何接收到它、最终哪行 create/save 真正落库。不能只说“创建副本”“关联起来”。

## 字段嵌入代码解释

- 语法与业务目的结合讲。遇到理解障碍时解释相关括号、冒号和缩进、字典访问/get、比较、not/and/or/is None、循环控制等规则；说明优先级与短路求值。新旧代码都要解释用户追问的原始写法，等价改写只作辅助，不可绕开原来的复杂条件。
- 不因用户是程序员就跳过其需要的语言基础；也不要因补语法而丢掉数据库读写和整段逻辑的连接。
- 首次使用关键字段时，就地说明业务含义、示例值、赋值者和读取者；不用先列出所有无关字段。
- 区分 ID/引用、来源标记、完整内容和计算结果。普通整数字段不等于数据库外键；查询条件不等于唯一约束。
- 用户问某字段有什么用时，给出该字段实际的“生成代码 → 保存代码 → 读取代码 → 判断代码 → 判断结果”，并解释它解决哪一步的问题。
- 用户追问 JSON 内容时，展开所需的内部键并说明如何解析。未解释的 rules、snapshot、data 不能充当黑盒。
- 代码后续读取的每个键，必须提前在对应对象的结构或生成代码中明确出现。例如读取 rule['version'] 和 result['winner']['id']，前面就要展示 rules 元素的 version、winner 内的 id，不能用省略号隐藏它们。只可省略本段没有消费的字段。
- 区分“读取已有字段”和“赋值新增字段”：result['rule_version'] = ... 是向字典新增/设置键，必须展示赋值前它尚不存在、右侧从哪里取值、赋值后的结构。原始查询对象、校验后对象、函数返回对象的字段可能不同；不能因为原始规则有 version 就声称 winner 也有 version。跨结构变换要展示相关字段的保留、丢弃或重命名。
- 示例数据前后一致，虚构数据明确标注。省略无关参数可以，但不能省略用户正在追问的查询、关联或赋值。
- 如果实际代码是“重算当前规则后比较来源的 ID/版本”，不能说成“用来源 ID 查询历史副本”。

## 数据库结构何时展开

仅在用户明确要求表结构、字段类型、全部字段时，补充相应数据库字典，并继续把字段对应回读写代码。默认不输出几十行字段清单。

未经线上 DDL 验证的类型标明来自模型。说明副本到底是另一张表，还是某行的 JSON；不要把规则版本号解释成一个不存在的副本 ID。

## 闭环与范围

- 根据问题范围讲清“读取 → 解析/判断 → 生成 → 保存 → 后续读取使用”。涉及账目调整时，还要接到结果如何写回账目；窄问题只展开相关环节。
- 说明相关事务边界；源数据被修改或删除是否影响已存数据，以真实代码为准。
- 用户说“类似这段示例”时，以其认可的代码讲解结构为准，不再扩大成业务长文或数据库百科。
- 解释任务不授权修改业务代码、迁移数据库或部署。不要为讲解而执行真实写入。

交付前自查：用户能否对照源码，看出每个关键变量从哪来、读写哪个字段、何时落库、下一步怎样消费？凡是需要猜测的关键箭头，补对应代码。

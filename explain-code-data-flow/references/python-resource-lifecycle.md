# Python 资源清理的详细讲解参考

用于用户不熟悉 Python，且正在追问连接、游标、`with`、`yield`、`finally`、返回值或请求范围时。下面是讲解方法和教学示例，不是任意项目的实际实现；真实行为必须先阅读当前源码。

## 先分清三个对象

- 连接：应用与数据库之间的会话。`connection.close()` 结束此连接；是否回到连接池，要看实际驱动和包装器。
- 游标：由连接创建，用于执行 SQL、读取本次结果的对象。关闭游标不等于关闭创建它的连接。同一连接可先后创建多个游标。
- 已取回结果：例如 `fetchall()` 返回到 Python 内存中的一组字典。普通已完整取回的数据在游标关闭后仍可使用；流式游标或尚未读取的数据不能据此类推。

先用真实代码中的名字分别对应这三个对象，再解释关闭职责。C1、U1 等教学编号必须明确不是业务 ID。

## 拆开容易跳过的语法

对实际出现的代码就地解释：

- `def read_connection(factory, sql):` 定义函数，参数由调用方提供。`read_connection(dbfun, sql)` 传入函数本身；函数体里 `factory()` 才调用它。不要把“接收函数”误说为已经建立连接。
- `with manager() as db:` 的 `db` 接收进入管理范围时交出的对象。在 `@contextmanager` 修饰的生成器中，它对应 `yield value` 的 `value`，不是函数执行完才 `return` 出来的结果。
- `@contextmanager` 来自 `contextlib`。它把按约定在 `yield` 前后写进入/退出逻辑的函数包装成可用于 `with` 的对象。不能泛化成所有 `with` 都必须用 `yield` 实现。
- `yield connection` 暂停此函数，把 `connection` 交给 `as db`；随后执行调用方的 `with` 内部代码。离开该代码块时再恢复，正常继续或把异常交回相应位置处理。
- `try` 是需要执行并可能失败的主体；`except Exception as e` 捕获匹配异常并用 `e` 引用它；`finally` 在正常结束、返回或异常退出这些常规路径中执行清理。它不是只在失败时执行。进程强制终止不在这类保证之内。
- `return cursor.fetchall()` 先执行 `fetchall()` 得到结果，再从内到外退出已进入的管理范围并执行 `finally`，最后调用方才收到结果。若清理自身抛错且未处理，原本的返回也可能被异常替代。
- `self.connection = connection` 把引用保存在对象属性中，供下一次调用读取；`self.connection = None` 清除这处引用，本身不会调用 `close()`。
- `ContextVar(..., default=None)` 声明一个按执行上下文保存值的入口。`set()` 的返回值是恢复用的 token，`get()` 获取当前值，`reset(token)` 恢复之前的值。只有当前代码配合每次请求建立/恢复范围，才能进一步解释为请求范围，不能只凭变量类型就断言任何异步子任务绝对隔离。

## 按真实先后顺序画清理过程

针对类似 PMS 的嵌套结构，核实源码后可解释为：

```text
进入页面处理范围：尚未创建数据库连接
  第一次查询：建立 C1 → 创建 U1 → 执行 SQL → fetchall 得到 R1
    先退出查询计时范围（如果实际存在）
    再关闭 U1
    再退出本次连接借用范围：正常复用时保留 C1
    调用方收到 R1
  第二次查询：借用 C1 → 创建 U2 → 执行另一条 SQL → 得到 R2
    关闭 U2，保留 C1，再交回 R2
退出页面处理范围：清除上下文保存的引用并关闭 C1
```

查询数据仍执行两次，减少的是连接建立/断开的次数。它不自动产生结果缓存，也不等于连接跨 HTTP 请求长期保存。清理时机按实际中间件范围描述，不能把“服务端生成响应后”说成“浏览器加载完后”。

## 可运行的最小语法示例

此示例只演示 `yield`、`with`、`return` 和 `finally` 的顺序，不连接数据库，也不实现项目的复用策略。运行时应当得到代码末尾断言指定的事件序列。

```python
from contextlib import contextmanager

events = []

@contextmanager
def lend_connection():
    events.append("1. 进入借用范围")
    try:
        yield "C1"
    finally:
        events.append("4. 退出借用范围：此教学示例保留 C1")

def query():
    with lend_connection() as db:
        events.append("2. 查询使用 " + db)
        try:
            return [{"id": 7}]
        finally:
            events.append("3. 先清理本次游标")

rows = query()
events.append("5. 调用方收到返回数据")
assert rows == [{"id": 7}]
assert events == [
    "1. 进入借用范围",
    "2. 查询使用 C1",
    "3. 先清理本次游标",
    "4. 退出借用范围：此教学示例保留 C1",
    "5. 调用方收到返回数据",
]
print("\n".join(events))
```

## 新旧对比要保留分支

对 PMS 这类实现，不能把“每次保留连接”写成无条件结论。实际核实并解释：

- 指定 GET 页面且是普通读取时，是否进入复用范围，第一次与第二次查询分别发生什么。
- 不符合条件时，是否使用独立连接并在查询范围退出后关闭；有事务包装器时，`close()` 是否只是无操作委托。
- 查询失败时，是否标记连接不可再用，以及退出本次范围时由谁丢弃并关闭。
- 页面后续处理失败时，最外层是否仍清理连接。
- `autocommit(True)` 对语句事务边界和已提交数据可见性的作用。不要解释成结果缓存，不要许诺数据库隔离级别和并发更新顺序不支持的可见性。
